# Crescendo (ken-gei-prelude) — Antigravity Agent Rules

> このファイルを Antigravity IDE の Customizations → Rules → **+ Workspace** で
> 新規作成し、内容を貼り付けてください。保存先は `.agent/rules/crescendo.md` になります。
> Git管理下に置けば、コミットするだけでチームやエージェントの誰が使っても同じルールが適用されます。

## 0. このプロジェクトについて（前提知識）

- 愛知県立芸術大学の演奏会情報ポータル「Crescendo」。React 18 + TypeScript + Vite + Tailwind（フロント）、
  Cloudflare Pages Functions + D1 + KV（バックエンド）、GitHub Actions（CI/CD・cronスクレイピング）で構成される。
- **`main` に push すると `deploy.yml` が自動的に Cloudflare Pages へデプロイする。**
  つまりこのリポジトリでは「コミット＝即本番反映」に近い。壊れたコードのpushは即座にユーザー影響につながる。
- 毎日06:00 JSTに `cron.yml` が大学公式サイトを自動スクレイピングし、D1にデータを追加する。
  この自動化は今後も無人稼働し続けることが前提。

## 1. 最優先原則：現状を壊さない（回帰させない）

- 現在このサイトは実際に一般公開され稼働中である。**「動いているものを悪化させる変更」は最大のリスクとして扱うこと。**
- 変更前に、対象機能が今どう動いているか（UI・API・データフロー）を必ず確認してから着手する。
  「たぶんこうだろう」で推測実装をしない。
- 既存のAPIレスポンス形式・DBスキーマ・URLパス・ルーティングを変更する場合は、
  後方互換性を壊さないか（既存の演奏会データ、共有済みURL、カレンダー購読URL等が壊れないか）を必ず確認する。
- 破壊的変更が避けられない場合は、実装前に理由と影響範囲を明示し、マイグレーション/リダイレクトの計画を含めて提案する。
- 大きな変更は一度に全部やらず、小さく検証可能な単位に分割する。

## 2. スマホ・PC 両対応を必ず維持する

- このサイトは「スマホ対応・レスポンシブ」が売りの一つ。UIや機能を変更する際は、
  **PCビューポートとスマホビューポート（375px前後を目安）の両方で見た目・操作性を確認すること。**
- ブラウザエージェント（Antigravity内蔵）を使って、変更後に主要画面（ホーム / 演奏会一覧 / 演奏会詳細 / 登録フォーム / 管理画面）を
  両方のビューポートでスクリーンショット確認してから完了報告する。
- タッチ操作（フォーム入力、地図操作、カレンダー追加ボタン等）がスマホで問題なく動くか確認する。
- 新機能を追加する場合も、最初からレスポンシブ対応で実装する（PC先行で作ってスマホを後回しにしない）。

## 3. メンテナンスフリーで動き続ける仕組みを壊さない

- このプロジェクトの設計思想は「Cloudflare無料枠のみ・放置しても壊れない」自動運用。
  新機能を追加する際も、**運用者が定期的に手動対応しないと壊れる仕組みを増やさないこと。**
- 具体的に注意する点：
  - cron（`cron.yml` / `functions/api/cron/*`）のスクレイピング処理を変更する場合、
    大学サイトのHTML構造変化に対する耐性（パースエラー時にサイレントに失敗して気づけない、を避ける）を意識する。
  - Cloudflare無料枠の制限（D1・KV・Pages Functionsの呼び出し数等）を超えるような実装を追加しない。
    追加する場合は必ず見積もりを提示する。
  - 外部有料APIキーが必須になるような依存を勝手に追加しない（Google Maps URL解析など既存の「URL貼り付けで自動取得」方式を尊重する）。
  - Secrets（`ADMIN_PASSWORD`, `CONTACT_ENCRYPTION_KEY`, `CRON_SECRET` 等）をハードコードしたり、
    ログに出力したりしない。

## 4. テストを必ず行う（レビュー前提のセルフチェック）

- コードを変更したら、完了報告の前に必ず以下を実行し、結果を報告に含める：
  1. `npm run build` — ビルドが通ることを確認
  2. `npm run smoke:chromium`（既存のスモークテストスクリプト）があれば実行
  3. 変更箇所に関連するAPI（`functions/api/**`）は、可能であれば `wrangler dev` 等でローカル起動し、
     実際にリクエストを投げて動作確認する
  4. UI変更はブラウザエージェントで実際にレンダリング確認（PC/スマホ両方、上記2章参照）
- 自動テストが存在しない領域を変更した場合は、「テストが無いため手動確認した」ことを明記する。
  「テストしていません」で終わらせない。
- DBマイグレーション（`migrations/*.sql`）を追加する場合は、ローカルD1（`--local`）で先に適用して
  エラーが出ないことを確認してから、リモート適用手順を提案する（リモートへの `--remote` 実行は必ず確認を取ってから）。

## 5. 本番への安全な反映フロー

- **`main` への直接pushはデフォルトで避け、作業ブランチを切ってからPRを作成する運用を提案する。**
  （ユーザーが明示的に「mainに直接pushしてOK」と言った場合を除く。）
- 破壊的変更・DBマイグレーション・Secrets変更を伴う作業は、実行前に必ずユーザーに確認を取る。
- コミットメッセージは変更内容が分かるように具体的に書く（自動デプロイのトリガーになるため、
  何がリリースされたか後から追跡できることが重要）。

## 6. コーディング規約

- 既存のディレクトリ構成・命名規則（`src/components`, `src/pages`, `src/lib`, `functions/api`）に従う。
- TypeScriptの型は既存の `src/types/` に合わせる。`any` の多用を避ける。
- Tailwindの既存デザインシステム（Gold `#c4ab6e`〜、Navy `#0f1225`〜、Cormorant Garamond / Noto Serif JP / Noto Sans JP）を踏襲する。
  新しい色やフォントを勝手に追加しない。
- 新規パッケージ導入は最小限にとどめ、導入する場合は理由をユーザーに説明する。

## 7. 完了報告のフォーマット

作業完了時は必ず以下を含めて報告する：
- 何を変更したか（ファイル単位）
- PC/スマホ両方での確認結果（スクリーンショット可）
- 実行したテスト・確認手順とその結果
- 既存機能への影響有無
- 次にユーザーが確認・承認すべきこと（mainへのマージ、Secrets設定、DBマイグレーション適用など）
